# Local CEO — System Architecture & Technology Plan

## Project Vision

Local CEO will evolve from an inventory and invoicing system into an **AI-powered operating system for small businesses**.

Each company will have isolated data, its own members and roles, and AI agents that can analyze company information and eventually perform approved actions.

---

## 1. Core Architecture

Local CEO uses a multi-tenant SaaS architecture.

A user can belong to multiple companies and have a different role in each one.

```text
Supabase Auth User
        ↓
Application User
        ↓
Company Membership
        ↓
Company
        ↓
Business Modules + AI Agents
```

> **Important Design Rule:** Company-owned data must always be scoped by `companyId`.

The same user may be Owner of one company, Manager of another, and Advisor of a third without mixing permissions or data.

## 3. Multi-Tenant Data Model

The database separates authentication identity from application data and company membership.

### Identity & Membership Hierarchy

```text
Supabase auth.users
        │
        │ same UUID
        ▼
Application User
        │
        └── CompanyMembership
              ├── Company
              └── role metadata
```

Supabase Auth is responsible for authentication.

The application database stores Local CEO-specific user data, companies, memberships, and future business data.

### Current Core Entities

- `User`: Global application identity associated with Supabase Auth.
- `Company`: Multi-tenant organization entity.
- `CompanyMembership`: Join entity connecting `User` and `Company` with membership-specific role metadata.

### Future Core Entities

- `Invitation`: Pending organization invitation tokens.
- `Product` & `InventoryItem`: Inventory tracking entities.
- `Customer`: Customer profiles and contact information.
- `Invoice` & `InvoiceItem`: Invoicing and billing records.
- `Employee`: Employee profiles linked to companies.
- `AIAgent`, `AIConversation`, `AIMessage`: AI agent states and chat histories.

### Application User Identity

The application `User` uses the same UUID generated by Supabase Auth:

```text
Supabase auth.users.id
        =
public.User.id
```

This is a logical application relationship.

Prisma does not manage Supabase internal authentication tables.

### Membership Roles

Roles belong to `CompanyMembership`, not globally to `User`.

During Phase 3, role metadata remains intentionally simple.

The complete role and permission model will be implemented during Phase 4 — RBAC.

### Tenant-Owned Data

Future business tables will use the shared multi-tenant schema and contain `companyId`.

For example:

```text
Product
├── id
├── companyId
└── ...

Invoice
├── id
├── companyId
└── ...

Employee
├── id
├── companyId
└── ...
```

Local CEO will **not** create separate physical tables for each company.

## 4. Authentication, Roles & Invitations

### Current MVP Authentication Strategy

Authentication is intentionally limited to **Google OAuth through Supabase Auth**.

Current authentication flow:

```text
/login
  ↓
Continue with Google
  ↓
Google OAuth
  ↓
Supabase Auth
  ↓
/auth/callback
  ↓
Exchange OAuth code for Supabase session
  ↓
/home
```

The following authentication methods are not part of the current MVP:

- Email/password registration
- Email/password login
- Email confirmation
- Magic-link authentication
- Forgot password
- Reset password
- Additional OAuth providers

These may be introduced later if product requirements change.

### Application Flow

```text
Google Login
  ↓
User Home
  ↓
Companies
  ↓
Select/Create Company
  ↓
Company Workspace
```

Authentication and authorization remain separate concerns:

- **Supabase Auth** determines who the user is.
- **Application User** stores Local CEO-specific user information.
- **CompanyMembership** determines which companies the user belongs to.
- **RBAC** determines what the user may do inside each company.

### Membership-Specific Roles

Roles are stored on `CompanyMembership`, never globally on `User`.

The same authenticated user may therefore have different roles across different companies.

### Invitations

Future invitations will contain information such as:

- `companyId`
- invited email
- role
- secure token
- expiration
- status

Invitation functionality belongs to a later development phase.

## 5. Database & Prisma Architecture

Local CEO uses **Supabase PostgreSQL** as the application database and **Prisma ORM** for schema definition, migrations, and typed server-side database access.

Supabase remains responsible for:

```text
Supabase
├── Auth
│   └── auth.users
│
└── PostgreSQL
    └── public
        ├── User
        ├── Company
        ├── CompanyMembership
        └── future business tables
```

Prisma manages the Local CEO application schema in `public`.

Prisma must not manage Supabase internal schemas such as:

```text
auth
storage
realtime
```

### Database Connections

Local CEO uses two PostgreSQL connection modes.

```text
Next.js / Vercel runtime
        ↓
DATABASE_URL
        ↓
Supabase Transaction Pooler
port 6543
        ↓
Supabase PostgreSQL
```

```text
Prisma CLI / migrations
        ↓
DIRECT_URL
        ↓
Supabase Session Pooler
port 5432
        ↓
Supabase PostgreSQL
```

Database credentials are server-only.

They must never use the `NEXT_PUBLIC_` prefix.

### Schema Evolution

Database changes are managed through Prisma migrations.

Development workflow:

```text
Update prisma/schema.prisma
        ↓
prisma format
        ↓
prisma validate
        ↓
prisma migrate dev
        ↓
Review migration SQL
        ↓
Commit migration
```

Production deployments will use committed migrations rather than manually changing production tables.

## 6. AI Agent Architecture

AI agents belong to a company, not directly to a user.

Each agent receives controlled company context and can access only tools explicitly approved by the application.

```text
User
  ↓
Authentication
  ↓
Company Membership + Permissions
  ↓
Current Company Context
  ↓
AI Agent
  ↓
Approved Tools
  ↓
Company-scoped Database
```

### Initial AI Agent Tools

- `getSales()`
- `getInventory()`
- `getInvoices()`
- `getCustomers()`
- `getExpenses()`
- `getEmployees()`
- `getAnalytics()`

Initially these tools will be read-only.

Later, agents may execute controlled actions with explicit human approval.

## 8. Architectural Principles

1. **Multi-tenant by design**  
   Every company is an isolated tenant and all company-owned data must be scoped by `companyId`.

2. **Authentication and authorization are separate**  
   Supabase Auth proves identity. Company memberships and RBAC determine access.

3. **Application identity remains separate from authentication infrastructure**  
   Supabase owns authentication records. Local CEO owns application user data.

4. **Roles belong to memberships**  
   Roles must never be stored globally on the user.

5. **Server-side authorization**  
   Frontend visibility is never the sole security layer.

6. **Progressive data modeling**  
   Business tables are introduced when their corresponding features are implemented rather than designing the entire future schema upfront.

7. **AI is a controlled application layer**  
   LLMs do not receive unrestricted database access.

8. **Human approval for sensitive actions**  
   AI agents recommend first and act only through controlled application tools.

9. **Provider abstraction**  
   AI model providers can be replaced without rewriting core business logic.

10. **Start simple**  
    Continue with a single Next.js application before introducing separate backend services.
